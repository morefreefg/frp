## 本轮真实运行

Mac arm64 与 Linux amd64 分别运行本轮构建的两端程序，各完成以下流程：

1. 通过管理 API 从空状态初始化服务端，导入独立加密私钥包。
2. 导出配对码，初始化客户端；两字段地址配置自动保存。
3. 使用原版 `go-shadowsocks2 v0.1.5` 客户端，实际通过服务端 SS 入口访问
   客户端侧 HTTP 服务，并完成 UDP 回声请求。
4. 使用操作系统 TLS 客户端验证内置公开证书，确认协商 TLS 1.3 / `kaboo/1`；
   TLS 1.2 握手被拒绝。
5. 未带管理口令的 API 返回 401，跨源修改返回 403。
6. 磁盘 `settings.enc` 为认证密文，未包含 SS 密码或明文私钥；
   `endpoint.json` 只有 `ip`、`port`。主密钥权限为 0600。
7. 两个运行程序分别拒绝 `-c`、`--config`、`--version`，退出状态为 2。
8. 分别重启客户端和服务端，无需重新初始化即可恢复 TCP / UDP 转发。

另外完成一轮跨主机验收：Linux amd64 运行服务端，Mac arm64 运行客户端，
普通 SS 客户端连接 Linux 的 SS 入口。目标 HTTP 与 UDP 服务仅绑定 Mac 的
loopback 地址，两个方向均成功，证明出站访问发生在 Kaboo 客户端。

Ego Lite 另起隔离实例，从空状态通过实际页面完成：上传加密私钥包、填写解锁码、
服务端保存、取得配对码、客户端保存，以及等待页面显示 TCP / UDP 转发就绪。
保存后解锁码与配对输入框清空。页面截图保存在临时目录，不提交凭据。

最初 SS 探针的无长度 HTTP 响应校验超时，查明是原版探针转发器固定等待 5 秒
后才关闭本地连接。单独确认响应完整，随后改用带 Content-Length 的 HTTP
测试服务验证请求内容与转发；未通过修改产品绕过此检查。
